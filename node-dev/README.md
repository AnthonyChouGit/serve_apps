# Node.js & TypeScript Development & Build Guide

A containerized development environment for Node.js projects (with SSH & VS Code Remote integration) and a complete production TypeScript (`npm` + `tsc` + Docker `build/` bundle) setup guide.

```text
[Part 1: Containerized Dev Environment]
  VS Code Remote-SSH (:5555) ──> [node-dev Container (Ubuntu + NVM + Node 24)] ◄──> [dev_network]

[Part 2: TypeScript Build & Self-Contained Deployment Pipeline]
  src/*.ts ──(npm run build: tsc + copy assets)──> build/ (dist/ + package*.json + Dockerfile + compose + .env)
                                                        │
                                                        ▼ (cd build && docker compose up -d --build)
                                            [node:slim Production Container]
```

---

## 1. Containerized Node.js Development Environment

This folder contains a containerized development environment for Node.js projects, designed for seamless integration with VS Code.

### Features
- **Custom Dockerfile**: Builds a base Ubuntu image with Node.js and SSH server pre-configured.
- **Persistent Volumes**:
  - `./source:/root/source`: Your code goes here.
  - `./.vscode:/root/.vscode-server`: Persists your VS Code server extensions and configurations across container restarts.
- **Network**: Connects to the external `dev_network`.
- **Ports**:
  - SSH mapped to port `5555`.
  - Vite/React default port `5173` mapped to the host.

### Usage
1. Build and start the container:
   ```bash
   docker compose up -d --build
   ```
2. Connect to the container via SSH or use the VS Code "Remote - SSH" extension to connect to `localhost:5555`.

#### 🌐 External Networks
This setup uses an external Docker network named `dev_network` to communicate with other development containers (like databases).
- **How to create it**: If the network doesn't exist yet, you must create it manually before starting the container:
  ```bash
  docker network create dev_network
  ```
- **If you don't need it**: If this container doesn't need to talk to other containers via a shared network, you can remove or comment out the `networks` sections in `docker-compose.yml`.

## 2. Building a TypeScript Project with npm (Production Bundle Workflow)

This production-ready workflow compiles strict ESM TypeScript into a self-contained `build/` artifact directory alongside production manifests so it can be run locally or deployed via a minimal `node:slim` Docker image.

### 2.1 Recommended Project Structure

```text
.
├── Dockerfile                # Lightweight production container specification
├── docker-compose.yml        # Production Docker Compose configuration (App + DB)
├── init.sql                  # Optional database initialization script
├── package.json              # ESM manifest, scripts, and dependencies
├── package-lock.json         # Deterministic dependency lockfile
├── tsconfig.json             # Strict TypeScript compiler configuration
├── build/                    # Self-contained deployment artifact (generated by `npm run build`)
│   ├── dist/                 # Compiled JS, .d.ts declarations, and source maps
│   ├── Dockerfile
│   ├── docker-compose.yml
│   ├── package.json
│   ├── package-lock.json
│   ├── .env
│   └── init.sql
└── src/
    ├── main.ts               # Application entry point
    ├── example.env           # Environment configuration template
    └── test.env              # Local development environment file
```

### 2.2 Initialize Project & Install Dependencies

```bash
mkdir my-ts-app
cd my-ts-app
npm init -y

# Install TypeScript compiler, Node.js types, and tsx for direct TS execution in dev
npm install -D typescript @types/node tsx
```

- `typescript`: Provides the `tsc` compiler for static type checking and emitting JS/declarations.
- `@types/node`: Supplies type definitions for Node.js built-in APIs (`fs`, `path`, `process`, etc.).
- `tsx`: Executes `.ts` files directly during local development without a manual build step.

### 2.3 Complete `tsconfig.json` Configuration

Create `tsconfig.json` (or initialize with `npx tsc --init`) with strict ESM, type-safety, and decorator settings:

```jsonc
{
  // Visit https://aka.ms/tsconfig to read more about this file
  "compilerOptions": {
    // File Layout
    "rootDir": "./src",
    "outDir": "./build/dist",

    // Environment Settings
    // See also https://aka.ms/tsconfig/module
    "module": "nodenext",
    "target": "esnext",
    "lib": [
      "esnext"
    ],
    "types": [
      "node"
    ],

    // Other Outputs
    "sourceMap": true,
    "declaration": true,
    "declarationMap": true,

    // Stricter Typechecking Options
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,

    // Recommended Options
    "strict": true,
    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "noUncheckedSideEffectImports": true,
    "moduleDetection": "force",
    "skipLibCheck": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,

    // For TypeORM / Decorator Support
    "emitDecoratorMetadata": true,
    "experimentalDecorators": true
  },
  "include": [
    "src/**/*"
  ]
}
```

#### Key Compiler Options Explained
- **`"module": "nodenext"` & `"verbatimModuleSyntax": true`**: Enforces native Node.js ESM semantics. Use explicit `.js` extensions in relative imports (e.g., `import { run } from "./run.js";`) and explicit `import type` for type-only imports (`import type { User } from "./types.js";`).
- **`"noUncheckedIndexedAccess": true`**: Array and record index lookups (`arr[0]`, `map[key]`) include `undefined` in their return type, preventing silent runtime `TypeError` bugs.
- **`"exactOptionalPropertyTypes": true`**: Distinguishes between an omitted optional property and a property explicitly assigned `undefined`.
- **`"emitDecoratorMetadata": true` & `"experimentalDecorators": true`**: Required if using decorator-based libraries such as `typeorm` or `class-validator`.
- **`"sourceMap": true` / `"declaration": true` / `"declarationMap": true`**: Emits `.js.map`, `.d.ts`, and `.d.ts.map` into `build/dist/` for stack-trace debugging and type consumption.

### 2.4 Configure `package.json` (ESM & Self-Contained Build Script)

Set `"type": "module"` and configure scripts so `npm run build` outputs compiled code into `build/dist/` and packages everything needed for deployment into `build/`:

```json
{
  "name": "my-ts-app",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "type": "module",
  "scripts": {
    "test": "CONFIG_PATH=./src/test.env npx tsx src/main.ts",
    "typecheck": "tsc --noEmit",
    "build": "tsc && cp package.json build/package.json && cp package-lock.json build/package-lock.json && cp Dockerfile build/Dockerfile && cp docker-compose.yml build/docker-compose.yml && cp src/.env build/.env && cp init.sql build/init.sql",
    "start": "node ./build/dist/main.js"
  },
  "devDependencies": {
    "@types/node": "^26.1.1",
    "tsx": "^4.23.1",
    "typescript": "^7.0.2"
  }
}
```

> **How the `build/` artifact works**: Running `npm run build` first runs `tsc` (emitting compiled JS to `build/dist/`), then copies `package.json`, `package-lock.json`, `Dockerfile`, `docker-compose.yml`, `src/.env`, and `init.sql` into `build/`. This makes `build/` a clean, self-contained deployment bundle containing only compiled code and runtime manifests—without `src/` or `node_modules/`. (If your project does not use a database initialization script or `.env` copy, remove the corresponding `cp` clauses.)

### 2.5 Production `Dockerfile` & `docker-compose.yml`

#### `Dockerfile`
Designed to build cleanly inside the `build/` directory using `node:slim`, production-only dependencies (`npm ci --omit=dev`), and Node.js compile caching:

```dockerfile
FROM node:slim

WORKDIR /app
ENV NODE_ENV=production
ENV NODE_COMPILE_CACHE=/app/.cache

COPY package.json package-lock.json ./
RUN npm ci --omit=dev && npm cache clean --force

COPY dist/ ./dist/

CMD ["node", "dist/main.js"]
```

#### `docker-compose.yml` (Example with PostgreSQL)
```yaml
services:
  app:
    build: .
    container_name: my_ts_app
    restart: unless-stopped
    volumes:
      - ./.env:/app/.env:ro
      - ./cache:/app/.cache
    depends_on:
      - app_db

  app_db:
    image: postgres:18
    container_name: app_db
    volumes:
      - ./data:/var/lib/postgresql
      - ./init.sql:/docker-entrypoint-initdb.d/my_init.sql:ro
    environment:
      POSTGRES_USER: ${database_user}
      POSTGRES_PASSWORD: ${database_password}
      POSTGRES_DB: ${database_name}
    restart: unless-stopped
    ports:
      - "9432:5432"
```

### 2.6 Local Development, Build & Docker Deployment

#### 1. Local Development & Type Checking
```bash
# Run TypeScript directly in development with tsx
CONFIG_PATH=./src/test.env npx tsx src/main.ts
# or via npm script
npm test

# Run type checking without emitting files
npx tsc --noEmit
# or
npm run typecheck
```

#### 2. Build the Self-Contained `build/` Bundle

- **Option A: One-time Docker build (No local Node.js required)**
  ```bash
  docker run --rm -v "$(pwd):/app" -w /app node:slim sh -c "npm install && npm run build"
  ```
  > On Windows PowerShell, replace `$(pwd)` with `${PWD}`.

- **Option B: Local Node.js build**
  ```bash
  npm install
  npm run build
  ```

- **Run compiled production build locally**:
  ```bash
  npm start
  ```

#### 3. Launch Production Containers from `build/`
```bash
cd build
docker compose up -d --build
```
